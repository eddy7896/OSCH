# ADR-0008: API gateway foundations

- **Status:** Accepted (2026-10-15) — owner accepted all decisions
- **Builds on:** ADR-0001 (tenancy), ADR-0002 (Firebase Auth), ADR-0004 (money), ADR-0007 (roles)

## Context
Phase 1 turns the Nest scaffold into the single enforcement point: authenticate, resolve the school, authorise, audit, then call Data Connect. Several choices depend on facts that were checked against the installed packages and the npm registry on 2026-10-15 (evidence in `documentation/phase1_plan.md` §3).

## Decisions
1. **Node 22 is the repo floor** (`.nvmrc`, `engines`, CI, Docker). Evidence: `@angular-devkit/core@22` (via the Nest CLI) declares `^22.22.3 || ^24.15 || >=26`; `nestjs-pino@5.3.1` needs `>=22.12`; `@hey-api/openapi-ts@0.99` needs `>=22.18`; `jsdom@30` needs `^22.22.2`. This machine runs 20.20 and must upgrade (`nvm install 22`).
2. **Data access = the generated *Admin* Node SDK, wrapped in `packages/database`.** The CLI supports `generate.adminNodeSdk` in `connector.yaml` (verified in `firebase-tools@15.34.0` schema and by generating one in a scratch project): typed functions such as `createInvoice(dc, vars)` that call `dc.executeMutation('CreateInvoice', vars)` through `firebase-admin` (13.10.0 when this was written; **14.5.0 is installed**, it needs Node 22 like the rest of the stack), with `Int64String`/`UUIDString` types. The Phase 0 *client* SDK (`javascriptSdk`, browser flavour) is dropped from the gateway. `firebase-admin` documents that named operations "run with admin privileges and ignore all auth directives", so `NO_ACCESS` operations stay callable only by the gateway (runtime proof is acceptance criterion of P1-2).
3. **HTTP stack:** NestJS 12 + `class-validator`/`class-transformer` DTOs, `@nestjs/swagger@12` (OpenAPI), `@nestjs/config@12` with a class-validator schema for env (fail fast), `@nestjs/throttler@6.7`, `@nestjs/terminus@12` (health), `nestjs-pino@5` + `pino@10`, `helmet`. **Rejected:** `nestjs-zod@5.5` (peers `@nestjs/common ^10 || ^11`, no Nest 12 support), `zod`-based DTOs for the same reason.
4. **Request pipeline (deny by default):** request id → throttle → `AuthGuard` (Bearer ID token, `verifyIdToken`) → `TenantGuard` (explicit `X-School-Id`, validated against an ACTIVE `SchoolMember` of a non-suspended school) → `PermissionGuard` (`@Permission(resource, action)` mapped onto `packages/rbac`) → validation pipe (whitelist; unknown fields such as a body `schoolId` are rejected) → handler → exception filter. A route with neither `@Permission(...)` nor `@Public()` **fails application startup** and fails a test.
5. **Errors:** one JSON envelope `{ error: { code, message, requestId, details? } }` with a closed registry of machine codes (clients localise the text). Data Connect `ABORTED` from a failed `@check` maps to `403 TENANT_REFERENCE_FORBIDDEN` (never reveals whether the other school's row exists); `INVALID_ARGUMENT` to 400.
6. **Audit:** state-changing Data Connect mutations write their `AuditLog` row **inside the same `@transaction`** (atomic: no change without an audit row); the gateway's interceptor additionally records security events (auth failures, denials) and request metadata. A drift rule (planned in P1-2c) will require every Phase 1 mutation to contain `auditLog_insert`.
7. **Platform routes** (`/v1/platform/*`, SUPER_ADMIN only) are a separate namespace with no school context; tenant routes always carry one.
8. **Tests run against real emulators:** Data Connect emulator (PGlite, no Java) and the Firebase Auth emulator (built in; not in firebase-tools' Java-dependent list). A generated route matrix proves 401/403/404 behaviour for every route.

## Consequences
- The existing `apps/api-gateway/src/dataconnect-sdk` (client SDK) and its `@oruschools/erp-sdk` dependency are removed; the CI "SDK is current" step moves to the new output path.
- Money crosses the API as decimal strings (`Int64String`), parsed with `BigInt`.
- Main risk: every new mutation must remember its audit insert; the planned drift rule turns forgetting into a build failure instead of a review comment.
- Unverified until built: the exact behaviour of `verifyIdToken` against emulator-issued tokens, and `AsyncLocalStorage` vs request scope for tenant context (spike inside P1-3).

## Addendum (2026-10-15, P1-2a/b built and verified on the emulator)
- The generated Admin SDK lives in `packages/database/generated/erp-admin-sdk` (committed; CI fails if regeneration changes it) and is consumed only through `@oruschools/database`.
- **Runtime proof:** `npm run test:database` runs `packages/database` against the Data Connect emulator: a `NO_ACCESS` mutation (`CreateSchool`) succeeds as admin; reads are scoped by `schoolId`; a cross-tenant invoice is aborted.
- **Verified error shapes** (they differ from what the plan assumed): a failed `@check` returns `extensions.code` `PERMISSION_DENIED` plus `ABORTED`; a bad enum or uuid `INVALID_ARGUMENT`; a unique violation `ALREADY_EXISTS`; an unreachable server throws `app/network-error`. They map to `DatabaseError` kinds `FORBIDDEN_REFERENCE` (403), `INVALID_ARGUMENT` (400), `CONFLICT` (409), `UNAVAILABLE` (502), `INTERNAL` (500). Data Connect's own messages and `debugDetails` include SQL and the refusal reason, so `DatabaseError` carries fixed text and keeps the original only as `cause` for logs.
- Against the emulator the SDK needs `DATA_CONNECT_EMULATOR_HOST=host:port`; without it the SDK tries real Google credentials.
- **Error precedence (found in P1-2c):** a unique violation inside a rolled-back `@transaction` reports `ALREADY_EXISTS` plus `ABORTED`, so `ABORTED` alone is the weakest signal; the mapper checks `PERMISSION_DENIED`, then `ALREADY_EXISTS`, then `INVALID_ARGUMENT`, then `ABORTED`.
- **Audit rule enforced (`dc-audit`):** every mutation contains `auditLog_insert` inside its `@transaction`, unless listed with a written reason in `auditExemptOperations`; Phase 0 operations are listed and leave the list as their modules are built. Tenant-scope exemptions likewise carry reasons.
- Query results return uuids without dashes; compare after normalising. The invitation expiry check compares against `$now` supplied by the gateway (server time), not by a client.

## Addendum (2026-10-15, P1-3a built and verified against the Auth emulator)
- **The Auth emulator does not verify signatures.** With `FIREBASE_AUTH_EMULATOR_HOST` set, `verifyIdToken` accepted an unsigned `alg=none` token naming an existing uid and carrying `globalRole: SUPER_ADMIN` (it only checks that the uid exists). The gateway therefore **refuses to boot in production** if that variable is set (`env.ts`), same as `DATA_CONNECT_EMULATOR_HOST`. Never set either variable on a deployed environment.
- Verified: emulator tokens verify with `uid`, `email`, `email_verified`; custom claims appear only in tokens issued after `setCustomUserClaims` (the user must sign in again); garbage, empty and truncated tokens throw `auth/argument-error`; a disabled or deleted user is refused. Not verified: `checkRevoked` after `revokeRefreshTokens` (the emulator accepted the old token), and the production signature path (needs real Google certificates; the library's documented behaviour, not exercised here).
- `AuthGuard` returns one response for every failure (401 `AUTH_REQUIRED`); the reason class is logged without the token. `AUTH_CHECK_REVOKED` (default true) adds the disabled/revoked check at the cost of one Firebase lookup per request.
- The error envelope and closed code registry (`src/common/errors.ts`) landed here rather than in P1-5; validation and OpenAPI remain P1-5.

## Addendum (2026-10-16, P1-3b)
- **Route scopes (deny by default):** a route is a *tenant* route unless it says otherwise. It then needs an `X-School-Id` UUID and an ACTIVE membership of a school that is not suspended. Opt-outs: `@Public()` (no sign-in), `@UserScoped()` (signed in, no school: `/me`, accepting an invitation), `@Platform()` (SUPER_ADMIN only, ignores the header, `/v1/platform/*`).
- **Uniform denial:** an unknown school, a school the caller does not belong to, a suspended member and a SUPER_ADMIN without a membership all get the identical `403 FORBIDDEN`. Only an *active member* of a suspended school gets `403 SCHOOL_SUSPENDED` (they already know the school). A missing or malformed header is `400 INVALID_REQUEST` and never reaches the database. A database failure is `502`, never an allow.
- **Tenant context:** `req.tenant = { schoolId, userId, schoolRole }` is set only from the verified membership; a school id in the body or query is never read (tested, with mutants). No `AsyncLocalStorage` is used: handlers receive the context with `@Tenant()`, and 60 interleaved concurrent requests of different users and schools showed no leakage.
- **Cache:** only ALLOW decisions are cached, for `TENANT_CACHE_TTL_MS` (default 30 s, 0 = off, per gateway instance). Role or suspension changes must call `MembershipService.invalidate/invalidateSchool` (wired when those modules are built, P1-6); until then, and across several gateway instances, a change takes effect within the TTL. Denials are never cached, so a new member works at once.
- Guard order: throttler, `AuthGuard`, `TenantGuard`; `PermissionGuard` follows (P1-3c).

## Addendum (2026-10-16, P1-3c)
- **Every route carries one explicit access decision:** `@Public()`, `@UserScoped()` (self-service: only the caller's own data, no permission), or `@Permission(resource, action)` (checked against `packages/rbac`; `@Platform()` routes also carry one). `@Permission` throws at class-load time for an unknown resource or action, so a typo cannot silently mean "no check".
- **Startup refusal:** `RouteDecisionCheck` enumerates every registered route at boot and the application does not start if a route has no decision, has contradictory ones (`@Public` plus a permission, `@UserScoped` plus a permission), or carries a permission no role holds (a dead route; for `@Platform` routes, one SUPER_ADMIN does not hold). The runtime guard also fails closed (403) if a route ever reaches it without a decision.
- **Two namespaces, never merged:** tenant routes are authorised with the school role from the verified membership only; platform routes with the global claim only (tested with a spy on `authorize`). A SUPER_ADMIN who is also a TEACHER member of a school gets exactly the TEACHER rights there.
- **Handlers narrow by scope:** the guard puts `{ resource, action, scope }` on the request (`@Granted()`); `own` and `linked` scopes are applied by each handler's query, which the cross-tenant harness (P1-7) must cover per route.
- Guard order is now: throttler, `AuthGuard`, `TenantGuard`, `PermissionGuard`.

## Addendum (2026-10-16, P1-3d)
- **Record-level rules** (`permission/record-rules.ts`, pure functions) cover what the matrix cannot say: (1) nobody approves their own request, whatever their role (a Principal's own leave needs someone else); a leave approval whose owner is unknown is refused; (2) a `status` key in a leave *update* counts as a decision and needs `leave:approve`, so HR can edit details but not decide; (3) on the loaded record, `own` scope requires the caller to own it, `linked` scope requires a guardian link, and a record carrying another school's id is refused (defence in depth against a bad query).
- **Hook:** handlers call `RecordRules.assert({ tenant, granted, record, changes })` after loading the record and before writing, passing the record they actually loaded, never request values. A violation is the same opaque `403 FORBIDDEN` as a missing permission; the rule name is logged server-side only.
- Phase 3 leave handlers must call it; P1-7's route matrix should include a self-approval case for every `approve` route.

## Addendum (2026-10-16, P1-4)
- **Two kinds of audit record, deliberately separate.** (1) The durable record of a *change* is the `auditLog_insert` inside the operation's own `@transaction` (P1-2c). (2) *Security events* are recorded by the gateway: every 401/403 is a structured log line; a 403 for an **authenticated** caller on a matched route is also stored (`action: security.denied`, `entityType: Route`, `entityId: "METHOD /route/template"`, details: code, status, required resource and action). A System Admin therefore sees, for example, a Principal trying to create memberships.
- **Guards run before interceptors**, so refusals never reach an interceptor; they are captured in the exception filter (`ErrorEnvelopeFilter` -> `AuditService.securityEvent`). The `AuditInterceptor` only covers requests that reached a handler: one structured line per POST/PUT/PATCH/DELETE (uid, school, role, route template, declared action, outcome, status, duration), never a body, query, header or token.
- **Attribution rules:** the school column holds only the *verified* tenant; a school id the client merely claimed goes into `details.attemptedSchoolId` (UUID only). 401s are not stored (no actor to attribute). Unmatched routes (404 probes) are not stored.
- **Never in the way:** security-event handling is best effort and wrapped so that no failure (including a synchronous throw or a missing operation) can change the HTTP answer; at most 30 stored events per actor per minute (the log line is always written), so a flood of denied calls cannot fill the table. Per-instance counters, like the tenant cache.
- **Declared and checked:** every POST/PUT/PATCH/DELETE route carries `@Audit({ action, operation })` or `@NoAudit('reason')`, else the app does not boot; `@Audit` on a read is also refused. `auditBindingProblems` checks each `@Audit` against the real `mutations.gql`: the operation must exist and its `auditLog_insert` must record that exact action (so a rename on either side fails). The existing audited operations and their actions are pinned in a unit test.
- **Process note:** the unit tests for `routeProblems` and `@Permission` (P1-3c) had not been committed with that branch; they are restored here.
